## 修复 MQTT「设备未在 10 秒内回包」——回包取缓存方式错误

**现象**：`POST /api/cloud/bindWorkspace/{gateway}/{sn}`（`Dji.Application/Service/DjiDevice/CloudApi/OrgManage.cs`）报
`AppFriendlyException：设备未在 10 秒内回包`；MQTTX 在同一 broker 上能看到 `thing/product/8UUXN5600A07KY/requests_reply` 的回执，
且回执里的 `bid` 正是服务端生成的（说明请求已到机场、回执也到了 broker）。

**根因（用真实程序集 Dji.Application.dll + NewLife.Core 写探测程序验证）**：
- 收包侧 `MqttService.OnMqttMessageReceived` 把回包**原始 JSON 字符串**存入缓存，键 = `bid.Reply()`（`dji_Reply:{bid}`，TTL 30s）——这个设计是对的。
- 取缓存侧 `MqttGatewayPublish.WaitReplyAsync` 原来写的是 `_sysCache.Get<CloudMqData<TData>>(key)`：
  NewLife.Caching（`NewLife.Core.dll`，本项目 CacheType=Memory）的泛型 `Get<T>` 只在「值本身就是 T」或简单类型可转换时成功，
  **string → `CloudMqData<T>` 这类复杂类型会静默返回 null（不抛异常）**，于是循环空转到超时。
- 附带第二个坑：上云协议是 snake_case，只有 Newtonsoft + `SnakeCaseNamingStrategy`（即 `MqttJson`）能正确映射；NewLife 自带的 JSON 无此能力。

**探测结果（真实类型，回包原文）**：
| 取法 | 结果 |
|---|---|
| `cache.Get<CloudMqData<MqOutput<AirportBindStatusRequestReply>>>(key)`（旧代码） | **null** |
| `cache.Get<string>(key)` → `MqttJson` 反序列化（新代码） | ✅ BindStatus 1 条、组织名=凌皓空间 |
| 缓存里存强类型对象再 `Get<T>` | ✅ 可用（但不是多调用方共用的解） |

**修复**：`MqttGatewayPublish.WaitReplyAsync` 改为「先 `Get<string>` 取原文 → `MqttJson.Deserialize<CloudMqData<TData>>`」，
反序列化异常按坏报文记录日志并继续等待；超时异常里改打印真实下发主题（原来打印的是 gateway）。
`MqttService` 侧缓存原文字符串的逻辑**保持不变**（多调用方输出类型不同，确实该缓存原文）。

**影响面**：所有走 `PublishWithReplyAsync` / `PublishWithReplyDataAsync` 的接口（航线任务、媒体、OTA、日志等）此前都会超时，
不止 bindWorkspace 一个。

**验证**：`dotnet build Dji.Web.Entry` 0 错误。用户要求不做真机联调（机场在 VPN 内网），故未跑 HTTP 端到端。

**环境备忘**：`Cache.json` → `CacheType=Memory` + `Prefix=dji_`；MQTT 订阅含 `thing/product/+/requests_reply`；
本地登录 superadmin/123456 但图形验证码 `sys_captcha` 默认开启。

## 前端：dji_vue 直播页 `selectChannel` 未定义 + 通道播放地址缺失

**文件**：`D:\chenyanyi\dji\dji_vue\src\views\main\djiLive\index.vue`（与 dji_server 配套的前端仓库）

**问题**：模板 `@click="selectChannel(channel)"` 引用了从未定义的函数（git HEAD 里也不存在），Volar/vue-tsc 报「上不存在属性 selectChannel」，
运行时点击通道卡片会抛 `selectChannel is not a function`。

**连带发现的真实缺陷**：后端 `DjiLiveService.BuildChannelsAsync` 产出的 `LiveChannelOutput` **只有 `SessionId`，没有 `playUrl`/`hlsUrl`**

**修复**（+54/-2）：
1. 新增 `selectChannel(channel)`：选中并高亮；在播 → `previewChannel`；空闲 → 仅 `ElMessage.info` 提示，不动正在播放的画面；
   同一路已在播则直接 return，避免重建播放器闪断。
2. `previewChannel` 增加「无地址但有 sessionId/id 时先 `detailDjiLive` 取详情」的补齐逻辑，同时修好通道列表「观看」按钮。
3. `syncFromState` 原来每次轮询都无条件把 `activeVideoId` 重置为第一路在播通道，会吃掉用户的手动选择；
   改为「选中通道仍在列表里就保留高亮，否则再自动跟随」。

**验证**：esbuild 语法检查通过；`@vue/compiler-sfc` 编译模板 0 错误；`selectChannel` 已出现在 setup bindings（83 个绑定）中。

**环境备忘（dji_vue）**：`node_modules` 里装的是 ESLint 9.38，但仓库仍是 `.eslintrc` 旧格式且无 `eslint.config.js`，

## 续：设备「未在 10 秒内回包」的真正根因 —— 订阅被静默丢弃

用户反馈修复后仍超时。继续排查，结论是**上一处修复没问题，故障在更前面的「订阅」环节**，且被 MQTTnet 静默吞掉。

**证据链（全部来自用户自己的日志 `Dji.Web.Entry/logs/20260930_*.log`）**
1. 服务端下发 `airport_bind_status` 的 bid = `42709bf3-781a-4604-a8f2-738e84bfa31a`，
   与 MQTTX 抓到的回执 bid **完全一致** ⇒ 机场回的就是我们这条请求，回执已到 broker。
2. 该实例 00:54:36 连接成功并「开始订阅 9 个主题」，00:55:23 下发请求，
   00:55:29 仍在正常处理设备 `events`（并回 `events_reply`）⇒ 同一时刻连接是活的。
3. 但 00:55:33 超时，且当天**没有一条「报文解析失败」** ⇒ 回包根本没进 `OnMqttMessageReceived`。
4. `thing/product/+/requests_reply` 是订阅列表第 5 条，循环里没有任何日志暴露它的 SUBACK 结果。

**根因**：MQTTnet 对 SUBACK 里的失败码（EMQX 未授权 0x87=135、或 MQTT3.1.1 的 0x80=128）
**既不抛异常也不报错**，旧代码 `await SubscribeAsync(...)` 完全不看结果码 ⇒
「订阅被 broker 拒绝」与「订阅成功」在日志上完全一样，表现为「设备明明在线回包了却一直超时」。
最可能是 broker 侧授权（ACL）没给 `JavaServer` 账号 `thing/product/+/requests_reply` 的订阅权限。

**本地实验（自建 broker 对照，未动内网）**
- 起 aedes broker 把服务端指过去（只改 `bin/Debug/net10.0/Configuration/Dji.json`，有备份并已还原）。
- 关键结论 1：MQTTnet 5 **默认用 MQTT 5.0** 连接（`MqttClientFactory`/`MqttClientOptionsBuilder` 未设版本），
  aedes 0.51/1.2 只支持 v3/v4（`lib/handlers/connect.js` 判 `protocolVersion > 4` 即回 CONNACK 1），
  日志表现为 `MQTT 已连接 ... 结果:1`；**CONNACK 失败时 `ConnectAsync` 也正常返回**，
  于是旧代码打印「已连接」、`ConnectedAsync` 不触发、一条主题都不订阅，并以 5 秒周期无限重连且无任何错误日志。→ 已修。
- 关键结论 2：某个主题订阅抛异常时，旧实现的 `foreach` 会整体中断，**后续主题全部不再订阅且无日志**。→ 已修（逐主题 try/catch）。
